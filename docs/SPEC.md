# Docs Spec

本文档定义 `barcode` 屏幕保护程序的文档写作规范、模板和更新规则。项目文档优先服务维护者和 coding agent，帮助他们在修改 Next.js 页面、屏保组件、配置模型和工程流程前快速建立上下文。

## 核心原则

- 文档服务于修改代码，而不是复述代码。
- 文档目录可以映射源码主目录，但单篇文档应描述职责、边界、数据流和风险点。
- 优先记录稳定约定：公共接口、数据模型、构建流程、跨目录依赖和验证方式。
- 不为每个小文件写文档；只有核心模块、公共组件、关键流程和容易误改的地方需要独立文档。
- 修改核心逻辑时，同步检查相关文档和 `docs/MAP.md`。

## 文档类型

### 入口文档

入口文档说明文档系统如何使用，例如：

- `docs/README.md`
- `docs/MAP.md`
- `docs/SPEC.md`

### 模块文档

模块文档描述一个目录、功能域或核心能力，例如：

- `docs/architecture/overview.md`
- `docs/modules/barcode.md`
- `docs/modules/floating.md`

### 流程文档

流程文档描述开发、构建、部署、内容同步等工程操作，例如：

- `docs/workflows/development.md`
- `docs/workflows/development.md`

### 决策文档

决策文档记录重要背景和取舍，适合放在 `docs/decisions/` 中。命名建议使用递增编号：

```txt
docs/decisions/0001-docs-structure.md
docs/decisions/0002-content-model.md
```

## 单篇文档模板

模块文档建议使用以下模板。没有内容的章节可以省略，但核心模块至少应包含“模块视角”“实现视角”“修改指南”和“验证方式”。

```md
# Module Name

一句话说明这个模块负责什么。

## 模块视角

说明模块职责、使用场景、对外行为和不负责的边界。

## 实现视角

说明入口文件、关键文件、核心函数、公共接口和依赖关系。

## 数据模型

说明核心类型、字段含义、默认值、约束和兼容要求。

## 修改指南

说明常见改动应该从哪里开始，哪些文件需要一起看，哪些边界不要轻易突破。

## 验证方式

说明修改后应该运行的命令、检查的页面、构建产物或人工确认点。

## 相关文档

- `docs/MAP.md`
```

## 流程文档模板

```md
# Workflow Name

一句话说明这个流程用于什么场景。

## 触发场景

说明什么时候需要运行或修改这个流程。

## 输入与产物

说明输入文件、环境变量、命令参数和生成产物。

## 执行步骤

1. 第一步
2. 第二步
3. 第三步

## 常见问题

记录容易误判的失败原因和排查入口。

## 验证方式

说明如何确认流程成功。
```

## 决策文档模板

```md
# 0001 Decision Title

## 背景

说明当时为什么需要做这个决策。

## 决策

说明最终选择了什么方案。

## 取舍

说明收益、成本、风险和暂未解决的问题。

## 影响范围

列出受影响的源码路径、文档路径和工作流程。
```

## 更新规则

以下情况必须检查并视情况更新文档：

- 新增、删除或重命名核心目录。
- 修改公共组件 props、导出名称或复用边界。
- 修改 `AppConfig`、`BarcodeItemConfig`、`FloatingGroupConfig`、默认配置或运行态模型。
- 修改 `localStorage` key、配置导入导出、配置/runtime 兼容策略或重置行为。
- 修改条形码时间格式、floating 字符串格式、节点映射、拖拽缩放、Wake Lock、计时器或提醒逻辑。
- 修改 npm scripts、构建流程、部署流程或自动化脚本。
- 修改 Next.js、Tailwind CSS、TypeScript、ESLint 等工程配置。
- 修复一个依赖隐含知识的问题，且该知识未来可能再次影响维护。

以下情况通常不需要更新文档：

- 纯样式微调，且不改变组件接口和布局职责。
- 小范围文案修改，且不改变配置模型、交互流程和验证方式。
- 内部实现重排，且不改变入口文件、外部行为和验证方式。

## MAP.md 维护规则

`docs/MAP.md` 是文档系统的索引，应保持简洁和准确：

- 新增核心源码路径时，为它添加对应文档或建议文档路径。
- 删除源码路径时，同步移除或改写映射。
- 重命名源码路径时，同步更新 `Source Path`。
- 新建模块文档时，把 `Documentation` 从建议路径更新为实际路径。
- 同一个源码路径可以对应多个文档，但不要把同一个文档映射到过多无关路径。

## 写作风格

- 使用中文，语气清晰、直接、现代。
- 优先使用短段落和表格，减少长篇叙述。
- 文件路径、命令、类型名和函数名使用反引号。
- 解释“为什么这样设计”和“修改时要注意什么”，避免逐行解释源码。
- 对 agent 重要的信息要显式写出：入口文件、影响范围、验证命令、不要改动的边界。

## 最小可用文档集

没有文档的项目可以先创建以下四份文件：

```txt
docs/README.md
docs/MAP.md
docs/SPEC.md
docs/init.md
```

通用初始化流程见 `docs/init.md`。本项目的启动文档集为：

```txt
docs/architecture/overview.md
docs/modules/barcode.md
docs/modules/floating.md
docs/workflows/development.md
```

这一套足够让 coding agent 快速建立项目地图，并能随着后续改动持续扩展。
